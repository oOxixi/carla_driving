# XH-202602 CARLA 语音控制演示可视化改造需求

> 适用仓库：`oOxixi/carla_driving`  
> 目标分支：`carla_driving_rstar`  
> 用途：交给 Codex 直接进行演示界面/录屏可视化改造  
> 核心原则：**评委一眼看懂“听到了什么 → 看到了什么 → Qwen 怎么判断 → 安全层是否介入 → 车辆最终做了什么”**。  
> 本文只约束“展示层”，**不得为了画面效果修改控制逻辑、Qwen 决策逻辑、安全规则或场景判定**。

---

# 1. 改造目标

当前演示界面的问题不是信息太少，而是**展示的信息不能证明系统能力**：

- 只有 CARLA 车辆画面、场景名、语音文本和“期望动作”，评委看不到系统真正的处理过程；
- “期望动作”属于测试答案，不是系统输出，展示价值很低；
- 场景 ID、英文枚举、代码字段过多时，非开发人员难以理解；
- 方言、定速、保持车道等简单 case 如果逐个长时间展示，会显得系统只是“语音遥控车”；
- Qwen、多模态感知、安全仲裁、状态机和执行闭环是项目真正的技术亮点，但目前在画面上几乎不可见。

最终视觉效果必须达到：

> **不用讲代码，评委只看画面 3～5 秒，就知道：用户说了什么、系统识别了什么、当前道路发生了什么、AI 为什么这样决策、车辆最后怎么执行。**

---

# 2. 最重要的展示原则

## 2.1 中文优先，英文只保留真正必要的技术名词

界面主信息全部使用中文。

允许保留的英文只包括少量不可替代的技术名词，例如：

- `Qwen`
- `CARLA`
- `TTC`
- `RGB`
- `LiDAR`

以下内容**不要直接大面积展示给评委**：

- `DrivingCommand`
- `CommandEnvelope`
- `BehaviorFSM`
- `ExecutionFeedback`
- `RawControl`
- `FinalControl`
- `PlanValidator`
- `PlanCompiler`
- `command_id`
- `target_id`
- `SAFETY_OVERRIDE`
- 完整 JSON
- 完整文件路径
- UUID
- 内部类名/模块名

如确实需要，可在调试模式显示；正式演示默认隐藏。

推荐中文映射：

| 内部字段/模块 | 演示界面显示 |
|---|---|
| DrivingCommand | 语音指令 |
| DecisionPlan | AI 决策 |
| BehaviorFSM | 当前驾驶状态 |
| PerceptionState | 场景感知 |
| Safety Supervisor | 安全监督 |
| SAFETY_OVERRIDE | 安全接管 |
| ExecutionFeedback | 执行结果 |
| target_id | 目标车辆 / 目标障碍 |
| command_id | 不展示 |
| RawControl | 不展示 |
| FinalControl | 最终动作 |

---

## 2.2 只展示“影响当前决策”的信息

不要为了证明系统复杂，把所有内部变量都堆在屏幕上。

每个时刻只回答五个问题：

1. **用户说了什么？**
2. **系统理解成什么？**
3. **当前场景里什么信息最重要？**
4. **Qwen / 安全层最终决定做什么？**
5. **车辆现在执行到哪一步？**

任何不能帮助回答这五个问题的信息，都不应进入正式视频主界面。

---

## 2.3 “系统实际输出”必须高于“测试期望”

正式演示中：

**禁止把“期望动作：XXX”作为主展示内容。**

应该改成：

- 识别结果
- AI 决策
- 安全结果
- 最终动作
- 执行状态

例如当前旧界面：

```text
静态障碍 | SUP_A10_static_vehicle_center
语音输入：台湾国语：“慢点开”
期望动作：SLOW_DOWN / SAFE STOP
```

建议替换为：

```text
用户语音
台湾国语｜“慢点开”

系统理解
减速

场景感知
前方静止车辆 28 m

AI 决策
降低目标速度

安全监督
正常

车辆执行
18 → 10 km/h｜减速中
```

测试场景 ID 可以保留为右下角小字，例如：

```text
场景：SUP_A10
```

而不是占据视觉中心。

# 3. 推荐总体布局

## 3.1 画布

正式录制统一按：

- 分辨率：`1920 × 1080`
- 比例：`16:9`
- CARLA 主画面：约占宽度 `70%～75%`
- 信息面板：约占宽度 `25%～30%`
- 不使用遮挡道路的大面积底部黑框
- 四周留安全边距
- 正式模式不出现终端、debug console、FPS 日志瀑布

推荐结构：

```text
┌──────────────────────────────────────────┬───────────────────────┐
│                                          │ 当前任务              │
│                                          │ ───────────────────   │
│                                          │ 用户语音              │
│            CARLA 主画面                  │ 系统理解              │
│                                          │                       │
│                                          │ 场景感知              │
│                                          │ AI 决策               │
│                                          │ 安全监督              │
│                                          │                       │
│                                          │ 车辆执行              │
├──────────────────────────────────────────┴───────────────────────┤
│  语音 → 识别完成 → Qwen 推理 → 安全校验 → 执行中 / 已完成        │
└──────────────────────────────────────────────────────────────────┘
```

# 4. 右侧信息面板：只保留 6 个核心区域

右侧面板是正式演示最关键的部分。

## 4.1 当前任务

顶部只显示自然语言任务名，不突出内部场景 ID。

示例：

```text
当前任务
红灯冲突安全处理
```

或：

```text
当前任务
多目标跟车
```

小字可以补：

```text
场景 SUP_B07
```

---

## 4.2 用户语音

需要让观众明确知道“系统刚刚听到了什么”。

推荐：

```text
用户语音
台湾国语
“慢点开”
```

方言名称做小标签，不要把“台湾国语 / 陕西话 / 粤语”等做成巨大标题。

如果存在 ASR 识别文本和原始播放文本差异，可展示：

```text
用户语音
粤语｜“马上刹车”

识别文本
“马上停车”
```

但如果两者完全一致，不要重复显示两遍。

---

## 4.3 系统理解

展示自然语言意义，不展示内部枚举。

错误示例：

```text
INTENT = AVOID_OBSTACLE
direction = LEFT
target = STATIC_VEHICLE
```

推荐：

```text
系统理解
从左侧绕过前方障碍
```

或者：

```text
系统理解
跟随正前方车辆
保持安全距离
```

速度指令：

```text
系统理解
目标速度：20 km/h
```

---

## 4.4 场景感知

这是多模态能力是否“看得见”的核心。

只展示**当前与决策直接相关的 2～4 项信息**。

正常定速时：

```text
场景感知
道路：当前车道正常
前方：无高风险目标
```

前车急刹时：

```text
场景感知
前车距离：12.6 m
相对速度：-4.8 m/s
碰撞风险：升高
```

红灯场景：

```text
场景感知
交通灯：红灯
停止线：11.4 m
```

施工绕障：

```text
场景感知
前方：施工障碍
右侧：可绕行
```

多目标：

```text
场景感知
候选车辆：3
已选目标：正前方车辆
距离：15.2 m
```

传感器失效：

```text
场景感知
摄像头：失效
LiDAR：正常
系统：降级运行
```

不要显示：

- RGB 帧号
- LiDAR 点数
- bbox 全量列表
- 所有 actor ID
- 所有传感器时间戳
- source_by_field 全量内容
- 一长串 TTC/距离/速度 debug

---

# 5. Qwen 展示方式

Qwen 是项目亮点，但**不能把模型输出 JSON 贴满屏幕**。

## 5.1 Qwen 状态

使用一条极简进度：

```text
Qwen
已接收 → 推理中 → 决策完成
```

正式视频最多使用以下 4 个状态：

- 等待语音
- 推理中
- 决策完成
- 超时/失败

不要展示 token 数、prompt、完整响应、API URL 等工程细节。

---

## 5.2 AI 决策内容

正常情况最多三行：

```text
AI 决策
动作：右侧绕行
目标：前方施工区域
依据：左侧受限，右侧空间可用
```

跟车：

```text
AI 决策
动作：跟随前车
目标：正前方车辆
策略：保持安全距离
```

红灯冲突：

```text
AI 决策
用户希望继续前进
```

然后由安全模块明确接管：

```text
安全监督
检测到红灯
拒绝继续前进
```

这样才能清楚展示：

**Qwen 负责理解与高层判断，安全层拥有最终否决权。**

---

# 6. 安全监督必须做成“强视觉事件”

项目最值得展示的不是“车听话”，而是：

> **危险的时候，系统不会盲目听话。**

因此安全状态只设三档：

### 正常

```text
安全监督
正常
```

使用淡绿色或青色。

### 风险提示

```text
安全监督
前车快速减速
正在降低目标速度
```

使用浅橙色。

### 安全接管

```text
安全接管
红灯禁止通行
最终动作：停车
```

使用红色强调。

安全接管发生时：

- 右侧卡片可以短暂放大/高亮 1～2 秒；
- CARLA 主画面不被大弹窗遮挡；
- 底部时间线将“安全校验”节点变红；
- 不要弹出十几行报警日志。

---

# 7. 车辆执行信息

车辆执行区域必须让观众看到“系统真的做了”。

推荐固定展示：

```text
车辆执行
速度：18.2 → 10.0 km/h
动作：减速
状态：执行中
```

绕障：

```text
车辆执行
动作：右侧绕行
状态：绕障中
```

完成后：

```text
车辆执行
动作：右侧绕行
状态：已完成
```

停车：

```text
车辆执行
速度：8.6 → 0 km/h
状态：安全停车
```

最多额外显示一个关键驾驶指标。

不要长期显示：

- throttle
- brake
- steer
- PID P/I/D
- cross track error
- raw control
- final control 数组

这些只适合开发调试模式。

---

# 8. 底部事件时间线

建议用高度很低的一条状态线代替现在的大面积字幕框。

统一固定为：

```text
语音输入  →  识别完成  →  Qwen决策  →  安全校验  →  车辆执行
```

颜色规则：

- 未到达：灰色
- 当前步骤：蓝色
- 已完成：青绿色
- 安全接管：红色
- 超时：橙色

这条时间线的意义是让评委快速理解系统不是“语音直接控制汽车”。

---

# 9. CARLA 主画面应该怎样处理

## 9.1 不要永远使用同一个远距离第三人称视角

根据场景选择视角：

| 场景 | 推荐主视角 |
|---|---|
| 定速 / 车道保持 | 后上方第三人称 |
| 前车跟随 | 驾驶员前视 / 后上方 |
| 前车急刹 | 后上方 |
| 红灯冲突 | 驾驶员前视 |
| 行人横穿 | 前视 |
| 绕障 / 变道 | 高位第三人称或轻度鸟瞰 |
| 多目标选择 | 高位第三人称 |
| 故障降级 | 保持当前视角，突出右侧状态 |

目标是让车辆动作“肉眼可见”。

例如绕障场景如果摄像机离车太远或者角度正后方，车辆横向位移不明显，视觉上就等于没演示。

---

## 9.2 感知框不要满屏

如果需要展示检测：

- 只框当前决策目标；
- 当前目标使用明显但不刺眼的边框；
- 标签写中文，如“目标前车”“行人”“施工障碍”；
- 不显示大量置信度小数；
- 非当前目标可以只保留淡框，甚至不显示。

多目标跟车场景推荐：

```text
[目标前车]
距离 14.8 m
```

而不是：

```text
vehicle.tesla.model3
track_id=493
conf=0.887621
bbox=(...)
```

后者非常符合工程师审美，也非常不符合演示视频审美。

---

# 10. 五类场景的专用可视化模板

正式视频不要让所有场景共用完全一样的信息权重。

## 10.1 普通语音控制

适用于：

- 设置速度
- 减速
- 保持车道

重点显示：

```text
用户语音
↓
系统理解
↓
Qwen 决策
↓
车辆执行
```

场景感知只占很小区域。

---

## 10.2 多目标跟车

重点必须突出：

```text
用户语音
“跟着正前方那辆车”

场景感知
候选车辆：3
已选目标：正前方车辆
距离：14.2 m

AI 决策
跟随目标车辆
保持安全距离
```

CARLA 主画面只高亮被选择的目标车辆。

这个场景证明的不是“FOLLOW”三个英文字母，而是：

**自然语言中的空间指代能够与真实场景目标完成绑定。**

---

## 10.3 红灯指令冲突

这是演示视频最高价值场景之一。

界面应形成非常明显的对比：

```text
用户语音
“不用停，继续往前开”

系统理解
继续前进

场景感知
交通灯：红灯

安全接管
禁止通行
最终动作：停车

车辆执行
速度 → 0 km/h
```

必须让评委看到：

**用户命令 ≠ 最终安全动作。**

---

## 10.4 动态风险 / 前车急刹 / 行人横穿

重点不需要展示很多 Qwen 内容。

应该突出风险变化：

```text
场景感知
前车快速减速
距离：9.8 m
碰撞风险：高

安全监督
立即减速

车辆执行
17.4 → 5.8 km/h
```

如有 TTC：

```text
预计碰撞时间：2.3 s
```

界面面向评委时可把 TTC 翻译成：

```text
碰撞风险：2.3 s
```

或者：

```text
预计碰撞时间：2.3 s
```

不要只写 `TTC=2.31`。

---

## 10.5 感知 / Qwen 故障

这是体现工程可靠性的场景。

### RGB 失效、LiDAR 正常

```text
系统状态
摄像头：失效
LiDAR：正常

运行模式
降级运行

最终动作
低速行驶 / 安全停车
```

### Qwen 超时

```text
Qwen
响应超时

安全策略
保持安全状态

最终动作
停车等待
```

重点让人理解：

**模型坏了 ≠ 车辆失控。**

---

# 11. 方言展示方式

方言不应该占整部视频的主要时长。

推荐做成 15～25 秒的快速蒙太奇。

每种方言只停留约 2～4 秒：

```text
粤语
“……”
✓ 识别成功
✓ 指令：减速
```

切换：

```text
陕西话
“……”
✓ 识别成功
✓ 指令：停车
```

切换：

```text
东北话
“……”
✓ 识别成功
✓ 指令：保持车道
```

最后：

```text
普通话 / 东北话 / 陕西话 / 粤语 / 台湾国语
多语言条件完成验证
```

不要让五种语言分别完整跑一遍“起步、定速、减速、停车”，否则重复度太高。

---

# 12. 色彩规范

建议延续技术报告现有风格，不重新造一套赛博朋克 HUD。

## 基础颜色

| 含义 | 建议颜色 |
|---|---|
| 普通信息 | 深灰 / 黑 |
| 语音输入 | 青色 |
| 系统理解 | 蓝色 |
| Qwen 决策 | 紫色 |
| 感知信息 | 青绿色 |
| 正常安全状态 | 绿色 |
| 风险 | 橙色 |
| 安全接管 / 错误 | 红色 |
| 未激活状态 | 灰色 |

建议使用低饱和度浅色背景 + 深色文字。

不要：

- 全黑 HUD + 荧光色；
- 七八种高饱和颜色同时出现；
- 每个模块一种完全不同颜色；
- 大面积渐变；
- 过度阴影、发光、动画。

正式比赛演示需要的是**科技感 + 可信感**，不是游戏直播插件。

---

# 13. 字体与字号

正式 1080P 视频建议：

- 一级模块标题：28～32 px
- 核心动作/安全状态：28～36 px
- 正文：22～26 px
- 次要说明：18～20 px
- 场景 ID 等调试信息：16～18 px

优先：

- 思源黑体
- Noto Sans CJK SC
- 微软雅黑

原则：

- 观众在普通笔记本全屏播放时也能直接读；
- 不使用超细字体；
- 数字与中文字号统一；
- 一块卡片不超过 4 行主要文字。

---

# 14. 动画规范

动画只用于表达“系统流程正在推进”。

推荐：

- 新语音进入：轻微淡入；
- Qwen 推理：状态点缓慢闪动；
- 决策完成：卡片切换；
- 安全接管：边框/标题短暂高亮；
- 执行完成：状态变为“已完成”。

禁止：

- 大量飞入飞出；
- 旋转图标；
- 连续跳动；
- 复杂 loading 动画；
- 任何会遮挡 CARLA 行驶画面的动画。

---

# 15. 正式演示模式与调试模式必须分离

建议实现两个显示模式。

## 正式演示模式

默认用于录制视频：

```text
--ui-mode demo
```

只显示：

- 当前任务
- 用户语音
- 系统理解
- 关键感知
- Qwen 决策
- 安全状态
- 车辆动作
- 流程时间线

## 调试模式

开发阶段使用：

```text
--ui-mode debug
```

可额外显示：

- command_id
- target_id
- 状态机状态
- throttle / brake / steer
- latency
- sensor validity
- frame id
- Qwen 原始结构化结果
- override reason code

**正式录屏绝对不要默认使用 debug 模式。**

# 16. 数据刷新规则

为了避免 UI 闪烁和数字乱跳：

| 信息 | 更新方式 |
|---|---|
| 语音文本 | 事件触发 |
| 系统理解 | 每条命令更新一次 |
| Qwen 状态 | 事件触发 |
| Qwen 决策 | 每次有效结果更新 |
| 感知距离/速度 | 5～10 Hz |
| 车辆速度 | 10 Hz |
| 安全状态 | 每帧内部检查，但 UI 状态变化时更新 |
| 执行状态 | 状态变化触发 |
| 时间线 | 事件触发 |

数字显示建议做轻度平滑，不要每帧抖动。

距离：

```text
14.28 m → 14.3 m
```

速度：

```text
13.874 km/h → 13.9 km/h
```

# 17. 状态保留时间

某个事件瞬间结束后不要立刻从屏幕消失，否则视频观众看不到。

推荐：

- 语音文本：保留到当前命令结束；
- Qwen 决策：保留到下一条命令；
- 安全接管：至少保留 2 秒；
- 执行成功：保留 2～3 秒；
- 传感器故障：故障存在期间持续展示；
- Qwen timeout：至少展示 2 秒，并同时展示最终安全动作。

# 19. Codex 实现要求

Codex 开始修改代码前，先完成以下检查：

1. 切换并确认当前分支为 `carla_driving_rstar`。
2. 找到当前正式 CARLA runner / demo runner。
3. 找到当前已有的画面绘制或视频录制代码。
4. 找到可读取的：
   - 语音事件；
   - ASR / NLU 结果；
   - Qwen 请求状态；
   - Qwen 高层决策；
   - Perception / State；
   - 当前车辆速度；
   - safety override；
   - command terminal status。
5. 只从已有运行状态读取数据，不重新实现一套决策逻辑。
6. 可视化代码必须和控制逻辑解耦。
7. UI 异常不得阻塞 CARLA 主循环。
8. UI 不得调用 `world.tick()`。
9. UI 不得直接修改 `throttle / brake / steer`。
10. UI 可以丢帧，但控制循环不能因为 UI 卡住。
11. 无字段时显示“暂无 / 未触发”，不要伪造默认值。
12. 所有 demo 字段都要能追溯到真实运行数据。

# 24. 与评分项的对应关系

可视化改造不能只追求“漂亮”，必须帮助评委看到评分项。

官方评分重点包括：

- 语音指令理解；
- 多模态信息融合；
- 语义与车辆动作对齐；
- 驾驶动作合理性；
- 模糊指令安全兜底；
- 实时性与稳定性；
- 创新与展示效果；
- 演示视频质量与可复测性。

所以界面至少应该在不同场景中让评委看到：

```text
语音
+
视觉 / LiDAR / 车辆状态 / 环境事实
+
Qwen 高层决策
+
安全约束
+
车辆最终执行
```

不能把视频拍成：

```text
“慢点开”
↓
车慢了
```

# 26. 最终效果标准

最终演示画面不追求“信息最多”，而追求下面这个判断：

> **随便截取视频中的一个关键时刻，一个第一次看项目的人，都能在 3～5 秒内回答：**
>
> 1. 驾驶员刚刚说了什么；
> 2. 系统理解成了什么；
> 3. 当前道路发生了什么；
> 4. AI 为什么做这个决定；
> 5. 安全层有没有改变 AI / 用户意图；
> 6. 车辆最终正在做什么。

如果一个界面需要开发人员在旁边解释：

> “这个 `FOLLOWING` 是状态机，然后这个 `target_id=17` 是前车，然后这里的 `override_reason=...`……”

说明这个界面仍然不适合正式比赛视频。

**正式演示不是把 debug 面板录下来，而是把系统能力翻译成评委能一眼理解的视觉语言。**
