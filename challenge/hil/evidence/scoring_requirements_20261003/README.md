# 初审评分细则要求的数据：B3 台账与缺口（2026-10-03）

> 依据：`2026年度中国青年科技创新"揭榜挂帅"擂台赛人工智能领域主擂台赛-初审评比方式及评分细则.pdf`
> （7 页，本地路径见本次对话引用的来源；本目录只保存**派生的分析结论**，不复制官方原文）。
> 本文件回答一件事：**细则要求的数据里，哪些我们已经能交、哪些现在按 0 分计、缺口的责任人在谁。**

## 1. 先看最要命的一条口径

细则「六、关键指标口径与判定依据」写着：

1. **实测优先**：性能指标以**官方部署环境**（面向车规级芯片的 X86 Docker 镜像 + 配套工具链）下
   **可复现的实测结果**为主要计分依据；纯软件理论推算、无实测支撑且无法复现的数据**不作为计分依据**。
2. **无法提供实测数据的指标项按 0 分计**，或由评委组结合材料合议认定。

所以下面每一项都要问两个问题：**这份数据是不是"实测"？能不能被复现？** 而不是"我们有没有算过"。

## 2. 挑战赛道（初审）50 分：逐项清点

| 评分项 | 分值 | 细则的判定数据 | 现在能不能交 | 缺口 / 责任人 |
|---|---:|---|---|---|
| **FLOPs 压缩比** | 15 | 轻量化后模型 FLOPs ÷ 原始模型 FLOPs；≤0.5 得 15 / ≤0.7 得 10 / ≤0.9 得 5 | **数据齐，但分母定义有风险**（见 §4.1） | 口径确认：A1 + 团队；B3 可复算 |
| **异构算力利用率** | 10 | CPU/GPU/NPU/DSP 在**端到端推理中的实际利用情况**，按组委会规则口径统计 | **交不出** → 现在按 0 分计 | 公式未冻结（B2/A4）＋ 需 A4 的 Runtime 实测；B3 的 `utilization_policy.py` 已就绪 |
| **核心指标衰减幅度** | 15 | 轻量化后**核心性能**相对原始模型的衰减（语音指令识别准确率、多模态语义对齐精度等）；≤3% 得 15 | **交不出** → 现在按 0 分计 | 需 B2 冻结 Benchmark + A3 同基准对比；B3 的 FP32↔INT8 漂移只是**代理指标**，不能当衰减 |
| **技术创新性** | 10 | 轻量化/适配策略的创新性与实用性（文本材料） | 素材在 A1/A2/A4/B4 手上 | B3 可提供"集成+量化一致性"的实测支撑 |

**当前最保守的自评**：15（若分母口径被接受）+ 0 + 0 + 待评 = **约 15/50**。
也就是说，**两份"0 分项"（异构利用率 10 分 + 核心指标衰减 15 分 = 25 分）是当前最大的分数风险**，
而它们都不在 B3 手里：一个等 B2/A4 的口径与 Runtime，一个等 B2 的冻结评测。

## 4. 需要团队先决策的三处口径

### 4.1 FLOPs 压缩比的分母（15 分的成/败）

细则原文只写"**轻量化后模型 FLOPs ÷ 原始模型 FLOPs**"。团队《后续统一执行方案》把它解释为
**相对 Teacher**，据此 A2 的 `analysis/flops_report.json` 给出：

| 口径 | 数值 | 对应档位 |
|---|---|---|
| 学生 FLOPs（固定 batch） | 498,640,896（参数 23,006,581） | — |
| Teacher 保守下界（单 token） | 2,818,572,288 | **比值 0.1769 → 15 分档** |
| 若"原始模型"被理解为**初赛提交的模型**（同一结构） | ≥1.0 | **0 分档** |

**建议**：材料里**显式写出分母定义**并**同时给出两个口径的数值**，避免评委按另一种理解判 0。

**数据一致性已核**（`flops_crosscheck.json`）：仓库里 A1 的 `challenge/flops_report.json` 与
A2 交接包中的副本，在 11 个关键字段（参数、MACs、FLOPs、教师下界、比值、口径说明、逐模块 MACs）
上**逐项一致、零差异**；两份都同样标注了"教师侧是 2B 级保守单 token 下界，不是精确模型 FLOPs"。
也就是说这条数据**不是某一方手填的**，可以放心引用（但分母口径仍需团队确认）。

### 4.2 异构算力利用率（10 分）

细则要求的是"**端到端推理中的实际利用情况**"，而我们目前只有两类"看起来像"的数据：

- **A4 尚未交付** Runtime，没有端到端推理；
- 我做的 **OE 编译预检**给出 59/59 节点落在 BPU —— 但那是**静态算子映射**，不是利用率；

→ 这条**必须等**官方/组委会公式 + A4 的 Runtime；`utilization_policy.py` 已按"公式一到即插即用"建好。

### 4.3 数据同源与可复现（影响所有性能项）

细则优先使用官方 1000 帧基准；允许自建数据集，但**必须说明来源、规模、口径，并冻结评测脚本**。
我们用的自建留出队列是 **6 个、共 850 例**（D2 v1.1 539 / gap300 123 / targeted-gap 99 / d3_wave2 56 /
turn-gap 29 / ms34 4），**脚本已冻结在 `challenge/hil/harness/`**，可以满足这一条；
但要在材料中写清"这是自建、这是口径"，不能含糊。

## 6. 按分数影响排序的下一步

1. **核心指标衰减（15 分）**：B2 冻结 Benchmark → A3 同基准对比 FP32/INT8 → B3 复核脚本可复现性；
2. **异构算力利用率（10 分）**：A4 交付 Runtime + 官方/组委会公式 → B3 用 `utilization_policy.py` 接入；
3. **FLOPs 分母口径（15 分）**：A1/团队确认并把两个口径都写进材料（B3 可复算）；
4. **把 B3 的 X86 实测搬到官方环境 + 最终候选**：延迟/内存/30 分钟长稳 → 直接产出材料 #10 与 #12；
5. 功耗：无板卡/无探针，材料中按细则写明"依赖实板，按官方口径处理"，不要用估算冒充实测。

## 7. 官方 X86 环境其实已经在手，而且**必须用它来测**（2026-10-03 补）

团队提醒得对：**官方要求的 X86 Docker + 工具链本地早就有了**，就是
`openexplorer/ai_toolchain_ubuntu_22_j6_cpu:v3.9.1`（指纹见 `official_env_fingerprint.txt`）：
Ubuntu 22.04.3 / Python 3.10.12 / torch 2.8.0+cpu / onnxruntime 1.19.0 / horizon_tc_ui 3.5.16 /
`hb_compile`、`hb_verifier`、X86 版 `hrt_model_exec` 齐备。我把它挂上仓库起了兄弟容器
（`harness/x86_sim/run_in_official_env.sh`），直接**在官方镜像里跑 B3 的测量链**。

### 7.1 三组同口径对照（同样 100 例、同样权重、同样代码）

| 环境 | preprocess p50 | 模型推理 p50 | **Planner E2E p50 / p95** |
|---|---:|---:|---:|
| Windows 宿主（py3.12） | 6.996 ms | 6.490 ms | 14.630 / 17.388 ms |
| **官方镜像 + 数据走 D: 挂载** | **75.716 ms** | 10.618 ms | **89.197 / 99.507 ms** |
| **官方镜像 + 数据在容器内** | 7.664 ms | 4.622 ms | **12.897 / 15.152 ms** |

**第一眼看到"官方环境慢 6×"是假象**：I/O 探针（`harness/x86_sim/probe_mount_io.py`）显示，
同一张 JPEG 从 Windows 盘挂载读要 **4.32 ms**，放进容器本地只要 **0.022 ms**（读取差 **200×**；
解码+缩放 5.84 ms → 0.43 ms，差 **14×**）。把数据放进容器后，**官方镜像反而是三者中最快的**。

### 7.2 这条对评分材料的两个直接结论

1. **可以现在就给出"官方环境下的实测"**：官方镜像内 E2E **P50 12.897 ms / P95 15.152 ms**，
   相对基础赛道"端到端响应时延 ≤150 ms"这一项有充足余量（注意口径差异：我们测的是 planner 链，
   不含语音前端，材料里要写明）。
2. **测量纪律（必须写进复现材料）**：在 Windows 上用 Docker 测延迟时，**数据集必须先复制进容器**
   （或放在 WSL 原生文件系统），否则走 `/mnt/d` 挂载会把延迟抬高约 **6×**——那会让 89 ms 这种
   虚高数字进材料。这条同样适用于官方复算，建议一并在材料里提示。

### 7.3 顺带记录

- 官方镜像自带 `torch 2.8.0+cpu` 与 `psutil`，所以 B3 的完整测量链（含 RSS/CPU 采样、30 分钟长稳）
  都能在该镜像内运行，不必额外安装；
- 兄弟容器 `b3_oe_repo` 只是把仓库挂进同一镜像，**随时可 `docker rm -f` 删除**，不影响原容器
  `b3_oe391_cpu`（后者仍用于编译与 X86 仿真）。
