# 语义理解链路重新审计（2026-11-03）

范围：当前语义实验分支和服务器正在运行的原方案。V6保持未启动，不改生产、旧权重或7B文件。
这是分阶段整改记录，不是“所有根因已证明”或新的性能通过报告。

## 1. 首要问题：三种契约不能混为一谈

| 层 | 实际输入/输出 | 已确认边界 |
| --- | --- | --- |
| 线上Planner V2 | 请求中含文本、targets、scene、constraints、command_hint；可附RGB；Qwen选一个字母动作码 | 不是模型直接生成完整多步任务；候选还会被解析意图/方向限制 |
| V1–V5语义LoRA | system＋原始文本→最多8步的action、原文目标、方向、参数、原文条件、禁止与确认 | 无RGB、前车动态或Actor ID；没有部署到线上；不是路况决策/车辆控制模型 |
| 控制执行 | ManeuverPlan V2的behavior、grounded target_id、m/s、枚举preconditions、completion、timeout等 | `PlanCompiler`不接受语义任务JSON；目前没有此任务输出到生产执行的接入路径 |

证据：`qwen_service/service.py`的`VllmQwenPlannerBackend`、`_choice_codes`、`_expanded_steps`；
`qwen_service/task_understanding.py`的`TaskUnderstandingPlanner`；`runtime/plan_compiler.py`的`compile`。
任务理解类的调用者检索仅发现离线工具及测试；服务端创建的是Planner V2 backend，不创建任务理解类。
线上模型的字母动作被适配器展开为步骤；恢复、返回等存在程序扩展，不能把这些扩展全归因于Qwen。
多个候选时Qwen仍可选择，附图时模型也可接收图像；但图像是否真正贡献需成对实验，不能仅凭代码存在断言。

服务器只读核验：PID6587 cwd为`carla-driving-main-optimization`，HEAD f92ac6fcc；
参数为`--qwen-mode planner_v2`、`--vllm-model Qwen/Qwen3.5-2B`，18005为READY；没有切换服务。
因此原驾驶效果与离线语义分数不能直接比较；把LoRA权重直接替换线上模型也不会自动补齐多步能力。

## 2. 动态路况目标尚未被当前训练任务表达

“设速21并跟车”在文本层表达用户目标，不说明前车此刻的速度、距离或是否已经停车。
纯文本条件字符串不是已经观测为真的状态；`target_text`也不是已关联的Actor ID。
同一文字输入在当前确定性文本模型上不能因为未输入的路况而产生可验证的不同动态决策。
缺少显式的速度作用范围/设定值与上限区分、任务进度、条件求值、目标关联和安全约束桥接。
这是契约与输入缺口，不应通过改用户指令、伪造图像、关键词替换动作或把安全层行为算作Qwen贡献来掩盖。
后续需保留文本意图，再另用真实路况生成高层执行决策；当前不改生产或提前定义未经审核的新执行契约。

## 3. 数据数量不等于语义覆盖

V5训练只有254条、54组、624步；其中FOLLOW112步，TURN_LEFT11步/6组，TURN_RIGHT12步/5组。
多数扩充来自构造模板和数值/目标替换，不是真实人类口语或大规模独立Teacher监督。
组平衡可调整训练曝光，不能创造未覆盖的语义边界。
18条条件口径已修订并获批准，但单条span合法不等于目标/条件在语义上正确；未改当前标签或再造审批。
已批准9条数据已冻结为338条新发布，只是下一轮候选材料，不代表对应错误已修好。

## 4. 模型错误与评分问题分别看

同一V3数据与提示下，第3轮结果：V3动作60/75、整条35/75；V4为63/75、33/75；V5为66/75、34/75。
V4相对V3新增整条正确5条、丢失7条，其中5条涉及错误条件。
V5仍有本车通过目标误判YIELD、STOP误判PULL_OVER、后续KEEP_LANE遗漏，且有禁止码非法、条件抄成动作等错误。
这些是真实生成错误；不能靠删除失败题或放宽schema消除。

严格整条匹配也包括字面span边界，不能简单称作“真实语义准确率”：例如短目标“行人”与更完整描述可能需人工判等。
保留原主评分和历史结果；新诊断单列格式、动作、禁止/确认、以及动作对齐后才计算的槽位差异。
槽位差异不能在动作已错位时逐下标硬比；span差异也不自动宣称是已独立判定的语义错误。
现行“任一基座正确动作不得退化”是本实验保护门槛，不是比赛官方标准。基座动作正确也不代表其所有槽位正确。

## 5. 尚缺证据：是否学会了训练样本

过去只有teacher-forced训练loss和Dev自主生成。低loss不能证明模型能独立生成同一条Train的完整任务。
当前只适配6个global-attention层的q/v、417792参数，也可能限制学习，但没有对照，不能直接认定容量不足或必须换7B。
需要同一已保存权重、同一prompt/解码，在原Train254条上自主生成，再与已有Dev75条比较：

- Train也差：优先查标签/输出表示、训练与生成一致性、优化和LoRA覆盖，不直接喊“泛化差”。
- Train好而Dev差：优先补组级多样性和边界对照，冻结新独立评测，避免继续在同一Dev上反复调参自证。
- Train/Dev都好而车辆执行差：重点查目标关联、条件/进度、计划编译和控制执行，不继续重训语言模型。

为此新增`diagnose.py`：只加载既有完成的2B adapter和原冻结Train，核验checkpoint及数据哈希、
不读Test标签、不更新参数、不部署。生成输入严格裁到assistant前缀，不把金标或错误列表喂给模型。
原`score_text`保持不变；诊断按完整/格式/动作/对齐槽位分类，原生成与主评分不修补。
Train结果只是记忆/拟合诊断，不是泛化成绩或晋升证明。

## 6. 修复顺序与停止条件

1. 已完成：核清链路和运行身份；修复诊断缺失，增加可复现的Train自主生成入口及错误分层测试。
2. 进行中/待运行证据：V5原Train254条推理诊断；先看结果再决定是否启动已经准备的V6。
3. 待第二步结果：对标签和具体边界分模块改进，一次只改一个因素，不再直接叠loss权重。
4. 文本理解稳定后：设计独立的目标关联/条件求值/任务进度与规划桥接；8步任务不能直接塞进4步执行计划或截断。
5. 接入前：新独立Test、同指令不同路况的模型输出对照、与规则基线的消融、完整安全回归及明确人工晋升。

不修改原冻结分支，不上传GitHub、不重启服务、不删除7B；每阶段有证据再往下做。
当前尚未证明单一根因，也没有声称真实闭环和独立测试已经通过。
